# .sbp: байтовый формат и операция импорта

## Совместимость динамической медиатеки — 5.1.27

Динамические ID имеют вид `user_<hex>` (загрузка) или `userN` (импорт), не более 64 ASCII-символов. Старые `user1`–`user8` сохраняются. Штатные `test`, `0`–`4` неизменяемы. Номер строки списка — только отображение, не идентификатор.

Фрейминг `.sbb` остаётся `SBBACKUP1`, `.sbp` — `SBPLAN1`. Версия находится в манифесте: `schoolbell-backup/2` используется для расширенных ID или более восьми пользовательских мелодий; `schoolbell-plan/2` — для более восьми пользовательских зависимостей. Кодеки читают версии 1 и 2; старый читатель обязан отклонить неизвестную версию. Для совместимых малых наборов экспорт сохраняет версию 1. В версии 2 нет квоты числа медиа/файлов; сохраняются проверки ссылок, целостности, размера манифеста и архива. Pages создаёт планы только со штатными мелодиями; пользовательское аудио допустимо для предварительной проверки импорта, без загрузки на GitHub.

Это частичный этап общей файловой политики: кодирование A–P, число расписаний/диапазонов и внутренние бюджеты расчёта ещё требуют отдельной миграции.

Ниже описан прежний этап; при расхождениях действует новая заметка о совместимости выше.

> Целевая политика обновлена в ТЗ 1.75, раздел 5.3: предметные квоты объектов/слотов заменены общим файловым допуском. Числа и правила слотов ниже описывают только существующий формат/реализацию. В 5.1.26 они ещё действуют до совместимого изменения кодирования, миграций и тестов; это не молчаливое изменение SBPLAN1. Обрезка существующих данных запрещена.

## 1. Контейнер

Предлагается знакомая потоковая раскладка .sbb, но с другим magic и строгим
отдельным валидатором. Импорт .sbp никогда не вызывает заменяющий restore .sbb.

| Часть | Точное представление |
| --- | --- |
| magic | ASCII `SBPLAN1` и LF, 8 байт |
| длина manifest | Ровно 8 десятичных цифр с ведущими нулями и LF, 9 байт |
| SHA256 manifest | 64 строчные hex-цифры и LF, 65 байт |
| manifest | Указанное число байт UTF-8 JSON, без BOM |
| payload | Файлы в порядке массива files, каждый ровно size_bytes, без разделителей |

Заголовок — 82 байта. CRLF, пробелы в числовом поле, нулевая длина manifest,
усечение и данные после последнего файла запрещены. Размеры считаются в байтах,
не символах. SHA вычисляется по исходным байтам, а не повторной сериализации JSON.
Дубли ключей, неизвестные поля, неверный UTF-8, null вместо обязательного значения,
нецелые размеры, отрицательные значения и глубина JSON больше16 отклоняются.
Порядок ключей JSON незначим; порядок массивов значим. Подписи автора здесь нет.

## 2. Поля manifest и calendar

Все перечисленные поля обязательны, кроме явно условных. Дополнительные поля
в версии1 запрещены. `format` — единственная версия схемы, версии экспортёра
не управляют совместимостью.

| manifest | Тип / ограничение |
| --- | --- |
| format | Строка `schoolbell-plan/1` |
| exporter | Объект `{name,version}`: name=`schoolbell-device` либо `schoolbell-pages`; version=`major.minor.patch`, до32 ASCII-байт, числовые части без ведущих нулей |
| timezone | Объект `{name,posix}`; name — точное имя из закреплённого списка зон модуля, до64 ASCII-байт; posix — соответствующее значение правил, до256 ASCII-байт, без CR/LF/NUL |
| files | Массив1…9 объектов `{name,size_bytes,sha256}` |
| media | Массив1…14 объектов каталога ниже |

Первый файл всегда `calendar.json` (1…12288 байт), далее только уникальные
`media/<sha256>.mp3` в лексикографическом порядке SHA. SHA — 64 строчные
hex-цифры, size_bytes — целое. Произвольные пути не разрешаются, архив не
распаковывается системным tar/zip. Имя пользовательского исходного файла не
управляет путём хранения; отображается поле title.

Каждая запись media содержит `{id,title,source,size_bytes,sha256}` и одно условное
поле: для source=`bundled` — `bundled_id`, для source=`user` — `file`.
id — локальный идентификатор `[A-Za-z0-9_-]{1,64}`; title — 1…96 UTF-8-байт,
не только пробелы, без управляющих символов. bundled_id: `test`, `0`…`4`.
У штатного источника нет payload; проверяются ID, размер и SHA установленной
поставки. У пользовательского file строго равен `media/<sha256>.mp3`, с теми же
size_bytes/SHA в files. Размер MP3 1…524288 байт; длительность не больше60 с.
Один payload может обслуживать несколько записей media с разными названиями.
ID и bundled_id уникальны в своих областях. Все файлы и записи каталога должны
быть достижимы из calendar; лишние и недостающие зависимости отклоняются.

`calendar.json` имеет ровно `{plans,schedules,pre_minutes,pre_media}`.

- plans: 1…8 записей `{id,name,start,end,schedule_ids,days}` текущей модели.
  Даты YYYY-MM-DD, годы0001…9999, границы включены, диапазоны не пересекаются.
  schedule_ids содержит до16 различных ссылок; days — по символу на дату,
  `.` означает тихую дату, `A`…`P` ссылаются на порядок schedule_ids.
- schedules: 0…16 записей `{id,name,color,rows}`; color обязательный1…16.
  rows без отдельного числового предела строк; строка `{id,time,media,enabled,pre}`.
  time — HH:MM, enabled/pre — JSON boolean, media — ссылка в manifest.media.
- pre_minutes — целое1…10; pre_media — ссылка в manifest.media, включается всегда,
  даже если выбранные строки не имеют pre. Все строки, включая отключённые,
  сохраняют зависимости. Все schedule_ids выбранных планов экспортируются,
  даже если отдельное расписание сейчас не используется символами days.
- ID — указанный ASCII-формат; плановые ID и ID расписаний уникальны отдельно,
  ID строк уникальны внутри расписания. Имена1…96 UTF-8-байт без управляющих
  символов и не только пробелы. Старое поле year экспортёр преобразует в диапазон.
  Режим, fixed_schedule и manual_media отсутствуют.

Модель дат не вводит отдельного лимита длительности: действует предел JSON и
итогового черновика. Экспортёр заполняет отсутствующий color текущим цветом UI.

## 3. Совместимость и добавление

Зона сравнивается по обоим полям name/posix, без догадок об эквивалентности алиасов.
Pages предлагает явно выбрать зону плана; зона браузера — только подсказка.
Устройство читает настроенную зону и проверяет соответствие действующим правилам.
Неопознанная зона либо расхождение правил — отказ с объяснением, без изменения
часов/TZ/NTP. UTC также задаётся записью из того же списка. DST неоднозначности
по-прежнему проверяет календарный вычислитель; совпадение строки зоны их не отменяет.

Свободные user-слоты назначаются в порядке user1…user8 по порядку записей media.
Занятые слоты не переиспользуются даже при совпадении SHA. Одинаковые байты внутри
архива передаются один раз, но разные записи user получают разные свободные слоты
и сохраняют свои названия. Это простое правило исключает неявное связывание правок.
Штатные записи отображаются по bundled_id. Совпадение предзвонка сравнивается по
size/SHA и интервалу, а не по номеру слота; действуют правила принятой политики.

Новые ID строятся как `imp-<operation_id>-p<N>`, `...-s<N>`, `...-r<N>`;
N — индекс с1, строка нумеруется внутри расписания. Проверка коллизий обязательна,
при коллизии операция отклоняется. Все ссылки переназначаются до сохранения.
Имена совпадают при точном сравнении UTF-8; автоматической нормализации/переименования
нет. Конфликтующие импортируемые имена пользователь меняет на preview.
Пересечения дат, включая общую граничную дату, запрещены.

## 4. Пределы и место

| Объект | Предел |
| --- | --- |
| manifest | 16384 байта |
| calendar и объединённый черновик | По12288 байт, до и после нормализации |
| Сумма уникальных пользовательских MP3 | 2097152 байта; итоговая медиатека дополнительно проходит собственную квоту |
| Весь контейнер | 2125906 байт =82+16384+12288+2097152 |
| Блок потокового аудио | 16384 байта; одновременно не более2 блоков байтового буфера |
| Изменения имён для preview | JSON до4096 байт |
| Preview/receipt JSON | Каждый до32768 байт |
| Незавершённая операция на устройстве | Одна, включая upload/preview/recovery |

Это пределы входа и байтовых буферов, **не обещание полного RSS**. JSON-объекты,
сериализованные копии, Lua, LuCI и валидатор MP3 потребляют дополнительную память.
До установки измерить пик host/target; отсутствие измеренного RSS нельзя скрывать
за размером потокового буфера. Длина HTTP проверяется рано, фактически прочитанные
байты ограничиваются независимо от Content-Length, включая chunked запросы.

Upload хранится в частной области tmp, не целиком в Lua-строке. Перед приёмом
резервируется оставшийся объём контейнера плюс128 КиБ метаданных; после записи
должно остаться max(1 МиБ,10% tmp-раздела). Проверка tmpfs не заменяет оценку RAM.
Загрузка прерывается после60 с без входных байтов или300 с общей длительности.

Постоянный staging формируется перед durable intent. Расчёт включает новые MP3,
временную и конечную копии при копировании, старую и новую метаинформацию,
блоки распределения и128 КиБ служебного запаса; существующие/удерживаемые данные
уже входят в занятую ёмкость. Поверх пика остаётся max(512 КиБ,10% раздела).
Если существующий менеджер требует больший запас — применяется больший.
Проверка повторяется под замками; ENOSPC обрабатывается и после неё.

## 5. API операции (предлагаемые LuCI actions)

Все методы требуют сессию администратора. Все POST — CSRF; GET ничего не меняет.
Браузер до POST создаёт криптографически случайный operation_id:32 строчные hex,
сохраняет его для разрешения неизвестного исхода. URI действий относительно
существующего маршрута модуля, не отдельный публичный сервис.

| Метод / action | Вход и результат |
| --- | --- |
| POST plan_import_upload | Multipart file + operation_id; bounded streaming; возвращает validated или rejected |
| POST plan_import_preview | JSON `{operation_id,names}`; names содержит maps plans/schedules: исходный ID → выбранное имя. Возвращает preview либо blockers |
| POST plan_import_commit | JSON `{operation_id,preview_token}`; только ранее подготовленный точный результат |
| GET plan_import_status | operation_id; текущее состояние/receipt, без повторной записи |
| POST plan_import_cancel | JSON `{operation_id}`; только до durable intent |
| POST plan_import_resume | JSON `{operation_id}`; явное продолжение после прерывания commit, без нового импорта |

Ответ: `{ok,operation_id,state,code}`, плюс только относящиеся к состоянию поля.
ok=true означает успешное обслуживание запроса; успех импорта означает исключительно
state=`committed`, не HTTP200 и не ok=true при preview.
Состояния: `receiving`, `validated`, `preview`, `committing`, `committed`,
`rejected`, `cancelled`, `expired`, `recovery_required`, `not_found`.
В ответе busy состояние текущей запрошенной операции не выдумывается:
state=`not_found` если она ещё не зарегистрирована, code=`busy`, ok=false.

preview содержит preview_token (64 hex), archive_sha256, draft_revision,
media_revision, plans/schedules/media mappings (old_id,new_id,name либо slot),
timezone, pre_change, space (required/free/reserve для tmp и постоянного раздела),
blockers — массив `{code,path}` до64 записей и blockers_truncated boolean.
При blockers подтверждение недоступно, preview_token не выдаётся.
pre_change содержит before/after с интервалом и идентификатором/хешем мелодии.
Ревизия empty допустима только для отсутствующего исходного черновика.

preview_token связывает архив, исходные ревизии, имена, отображение и итоговые
байты. Это серверный непрозрачный токен, не замена CSRF. Новый preview отменяет
предыдущий. Срок preview —15 минут по монотонным часам от выдачи, без продления
опросом. Reboot отменяет preview. До intent операция истекает через30 минут
неактивности; GET срок не продлевает. Durable intent не истекает автоматически.

При commit повторно проверяются ревизии, зона, выключенная автоматика, свободные
слоты и место. Исходный сохранённый draft должен совпадать с preview; UI также
блокирует импорт при несохранённых правках. Конфликт даёт новый preview, не скрытый
merge. Пока открыт preview, новые локальные правки делают кнопку подтверждения
недоступной. Последний ответ не должен перезаписать более свежие правки браузера.

committed содержит result `{draft_revision,media_revision,automatic_enabled:false}`
и отображения. Повтор того же commit возвращает receipt, не исполняет импорт снова.
Другой upload с тем же ID отвергается; повторные байты не создают новую операцию.
После потери ответа читается status. not_found не означает ни успеха, ни разрешения
повторить запись: сначала сверить текущие данные и при необходимости начать новый
preview. Сохраняются последние16 завершённых receipts (каждый до32 КиБ), удаление
только по порядку завершения, без зависимости от правильности настенных часов.
Их место входит в бюджет; неполная операция никогда не вытесняется.

code: `ok`, `busy`, `format`, `size`, `checksum`, `dependency`, `unsupported_media`,
`timezone`, `overlap`, `name_conflict`, `pre_conflict`, `slots`, `space`,
`automatic_enabled`, `conflict`, `expired`, `invalid_state`, `storage_unavailable`,
`recovery_required`, `not_found`. path не содержит персональных путей.
Auth:401/403; malformed:400; too large:413; conflicts/busy:409; semantic:422;
storage failure:503; admitted/read requests:200. UI также проверяет JSON/state,
поскольку отказ с HTTP200 возможен на старом маршруте. Авторизация применяется
до чтения тела; конкретную возможность ранней проверки LuCI проверить тестом.

## 6. Фиксация и восстановление

Порядок замков: player gate → editor → media. MP3 проверяется без звука.
Долгая загрузка/preview не держит эти замки. Commit не запускает проигрыватель.
Старые слоты/названия/данные не меняются; применённый план не заменяется.

1. Под замками повторить admission, сформировать будущие draft/catalog и
   постоянные staged-файлы. Проверить все хеши; sync файлов и каталогов.
2. Атомарно записать и sync `import.pending`: operation_id, точный результат,
   базовые/целевые ревизии и перечень SHA/длин staged-объектов. Это **durable intent**:
   до него отказ удаляет только собственный staging; после него отмена запрещена.
3. Пока маркер существует, все пути чтения/записи draft/media, активации,
   backup/restore и запуска звука видят recovery_required/committing.
   Диагностика/status и безопасное выключение доступны. Установка пакета также
   не должна уничтожать незавершённый staging. Маркер проверяется после reboot.
4. Опубликовать новые объекты/каталог и объединённый draft через существующие
   durable операции. Проверить целевые ревизии, ссылки, SHA и auto-off.
5. Записать и sync committed receipt; удалить pending и sync его каталог.
   Только после этого API возвращает committed. Если pending остался рядом с
   receipt, recovery сначала сверяет результат, затем завершает очистку.

Любое прерывание после intent оставляет явную блокировку. Resume под теми же
замками идемпотентно продолжает публикацию, если данные равны исходным либо
предусмотренным целевым ревизиям. Неожиданное изменение/утрата staging блокирует
продолжение; не подменяет его автоматическим rollback или удалением замков.
Статус после ошибки записи неизвестен до чтения durable records.
Выявление владельца оставшегося замка требует проверки процесса; один возраст
не доказывает, что замок можно снять. Активные автозвонки не разрешаются при pending.

Для Pages такой же admission выполняется над localStorage: весь объединённый
draft записывается одним значением, storage exception оставляет прежние данные.
Пользовательские медиа отклоняются до записи; никакие файлы не отправляются GitHub.
Многовкладочный конфликт нельзя решить одним localStorage.setItem: реализация
должна обеспечить взаимное исключение и повторную проверку ревизии либо отказать
в импорте при отсутствии поддерживаемого механизма блокировки.

## 7. Очередь реализации и проверки

1. Чистые JS/Lua кодеки и общий корпус байтовых векторов: границы длин/UTF-8,
   дубли ключей, truncated/trailing, SHA, ссылки. Без HTTP/записи устройства.
2. Чистая модель замыкания зависимостей, mapping и preview, включая все конфликты.
3. Экспорт/импорт Pages со штатными мелодиями, затем системный staging/commit API
   с fault injection после каждого write/sync/rename и потерей HTTP-ответов.
4. UI устройства, host-регрессии авторизации/лимитов; отдельно разрешённая
   установка после backup и перенос с пользовательскими MP3, автоoff.
5. После внедрения .sbp — отдельный протокол сквозной приёмки точного комплекта
   на новом устройстве того же типа: OpenWrt, установка, настройка, функционал,
   восстановление и недельный либо более длительный прогон с автоматикой.
   Состав/SHA артефактов и критерии фиксируются до опыта. Мониторинг состояния
   не доказывает слышимость; сеть в прогоне не доказывает работу без Интернета.
   Прошивка/звук/питание/автоматика согласуются перед соответствующими опытами.

### Контрольный вектор примитива (не допустимый план)

Для двух байтов UTF-8 `{}`: длина `00000002`, SHA256:
`44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`.
Это проверяет framing/hash, но семантический валидатор обязан отклонить такой
manifest. Полные допустимые векторы будут общими fixtures JS/Lua на первом этапе,
а не доказательством реализации по одному примеру в документе.

С 5.1.24 отдельные пределы числа строк сняты. Сохраняются размер черновика 12288 байт и бюджеты расчёта событий; вместимость зависит от данных. Большие планы могут не импортироваться старыми версиями — используйте совместимую версию устройства и Pages.
