# Подготовка и выпуск релизов

[English](RELEASING.en.md) · [Выбор способа установки](INSTALLATION.md) · [Формат комплекта](formats/release-bundle-v1.md) · [Заметки выпусков](releases/README.md)

## Можно ли выпустить незавершённую версию

Да: используйте GitHub **Pre-release** с точным перечнем работающих функций и
ограничений. **Draft** — неопубликованный черновик для подготовки; это другой признак.
Ни один из них не означает успешную аппаратную приёмку.
[Официальный порядок GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

Решение владельца от **25.11.2026**: публикация разрешена **как есть**. Незавершённые
материалы распространения НЕ блокируют упаковку или публикацию. Известные открытые
вопросы сохраняются в [аудите](LICENSE_AUDIT.md) как сведения, не как запрет.
Без --candidate сборщик формирует prerelease; с ним — локальный candidate. Оба режима
проверяют байты, состав, ABI и безопасные пути, не загружают файлы в GitHub.
Разрешение владельца не помечает незавершённый аудит или аппаратную приёмку выполненными:
manifest отдельно фиксирует publication.authorized=true и distribution_review.blocking=false.
Legacy distribution_cleared=false остаётся сведением о незавершённом аудите, не блокировкой.

| schoolbell-setup-wizard-v0.3.1-windows-x86_64.zip | Совместимая версия GUI, EXE, runtime и worker-файлы; версия независима от пакета |
| modbus-schoolbell_5.1.127_all.ipk | Отдельное приложение для специалистов; не полный набор зависимостей |
| Консольный комплект OpenWrt/OEM | Дополнительный самостоятельный способ; приложить только проверенную сборку и указать её точное имя в заметке |
| SHA256SUMS и SHA256SUMS.sig | Суммы всех поставляемых архивов/IPK и подпись существующим ключом проекта |
| Материалы лицензий и соответствующие исходники | Фактический состав для распространяемых бинарников; перечень в заметке выпуска |

Имена — для текущих версий, не предложение присвоить старую версию изменённому
мастеру. Исправление кода требует новой версии мастера перед выпуском.
GitHub Source code ZIP/TAR не заменяет готовые установочные архивы.

В мастере 0.3.0 встроены оба закреплённых образа OpenWrt/OEM. 25.11.2026
проверены возврат OEM и установка OpenWrt с последующей установкой Школьника;
смена SSH-ключа потребовала ручного исправления. Это ограничение preview. Мастер скачивания из GitHub ещё не имеет; пользователь скачивает
ZIP самостоятельно. Минимальная версия в manifest — проверка формата, не доказательство
совместимости конкретной пары EXE/ZIP.

## Контрольный список до тега

1. Выберите чистый подписанный commit после CI точного HEAD. Номер пакета, версия
   мастера, manifest и имя файлов должны совпадать с содержимым. Не создавайте тег
   на текущем незакоммиченном дереве.
2. Обновите docs/releases/v5.1.127.md (для новой версии — новый файл), CHANGELOG RU/EN,
   TODO и таблицу INSTALLATION. Укажите версии обоих продуктов, SHA принятой сборки,
   проверенные маршруты и ограничения. Удалите устаревшие «ещё не проверено» только
   при наличии соответствующего результата, не задним числом.
3. Выполните make all в WSL, профильные PowerShell/Qt-тесты, статическую Windows-сборку
   и проверку её DLL. Соберите ZIP пакетов в новый каталог:

   ```sh
   python3 scripts/build-schoolbell-release.py --bundle out/setup-gui-fresh-bundle --out out/release-preview
   ```

   Это локальная подготовка разрешённого pre-release, без загрузки в GitHub. Для кандидата добавьте --candidate. Каталог входного комплекта
   должен существовать и содержать текущие проверенные IPK. Упаковщик GUI с явным списком файлов: `python3 scripts/build-wizard-release.py --build out/setup-gui-external --out out/wizard-preview`. Не архивируйте рабочую папку целиком.
4. Проверьте распакованную поставку на чистой Windows 11: без MSYS2/Qt/Python хоста,
   с документированными системными зависимостями, из пути с пробелами/кириллицей.
   Не должны попадать пароли, ключи, сеансы, копии роутеров, логи и пользовательские ZIP.
5. Зафиксируйте точную пару архивов и хеши. На отдельно разрешённом стенде проверьте
   заявленные маршруты. Для незавершённых маршрутов допустим явный статус «недоступно»;
   нельзя выдавать испытание отдельных частей за сквозной PASS.
6. Приложите имеющиеся материалы распространения и перечислите открытые вопросы без блокировки выпуска. Проверьте SHA256SUMS и его подпись. Подпись
   Git-коммита не заменяет подпись файлов. Новый ключ ради выпуска не создаётся.
7. Владелец создаёт подписанный тег и Draft/Pre-release, прикладывает именно проверенные
   файлы, затем сверяет скачанные файлы с локальными суммами и публикует вручную.

## Команды владельца после прохождения условий

Пример для v5.1.127; не выполнять до завершения предыдущего списка. Сначала проверьте,
что тег ещё не существует и main указывает на принятый commit. Уже опубликованный
тег и файлы не заменяются: исправление выпуска получает новый номер.

```sh
git switch main
git pull --ff-only origin main
git status --short
git tag -s v5.1.127 -m "Schoolbell v5.1.127 preview"
git verify-tag v5.1.127
git push origin v5.1.127
gh release create v5.1.127 --verify-tag --draft --prerelease --latest=false --title "Школьник 5.1.127 — предварительный выпуск" --notes-file docs/releases/v5.1.127.md
```

Добавьте отдельными файлами проверенные assets через GitHub Release UI или
`gh release upload v5.1.127 <точные-пути-к-проверенным-файлам>`. Не используйте
`--clobber` и широкую маску рабочей папки. Публикация — отдельное действие владельца.
GitHub API также допускает draft=true и prerelease=true; это тот же порядок без gh.

Если предварительный выпуск позже становится стабильным без изменения байтов,
можно изменить его статус. Если меняются байты — новый выпуск/версия. Храните старые
совместимые архивы для восстановления; текущий README не должен менять инструкции
уже выпущенной версии — её сведения сохраняются в заметках и вложенных руководствах.

## Следующие завершённые группы

1. Закрыть сетевой опыт и исправление DHCP; подписанные коммиты и CI.
2. Встроить оба закреплённых образа, единый firmware-only механизм для CLI/GUI,

3. Проверить отдельно OEM → OpenWrt, OpenWrt → OEM и OEM → OEM через GUI; затем полный
   цикл с комплектом. Получение адреса или открытие порта не заменяет проверку версии.
4. Собрать переносимую поставку, имеющиеся материалы и подпись; проверить точную
   пару архивов, подготовить первый Draft/Pre-release. Загрузка релизов из самого GUI
   может быть добавлена после первого выпуска и не блокирует ручное скачивание.

## GitHub Actions: подготовка файлов

Workflow **Schoolbell release artifacts** (`release-artifacts.yml`) запускается вручную
через Actions → Run workflow. Выберите нужную ветку/commit. Он выполняет make all,
собирает настоящий MIPS clock и 35 IPK, статический Windows-мастер, проверяет встроенные
образы и запуск из распакованной папки с пробелом. Windows runner — Server 2022:
его проверка не заменяет приёмку на Windows 11.

Результат `schoolbell-windows-preview-<commit>` содержит два ZIP, IPK приложения,
`target-build.json`, `release-pair.json` и общий `SHA256SUMS`. Скачайте и распакуйте
внешний архив Actions; к Release прикладывайте вложенные файлы, не этот внешний ZIP.
Артефакт Actions хранится 30 дней; постоянное распространение — через Release.
Workflow не имеет contents:write, не создаёт тег/релиз и не использует ключ подписи.
Подпишите суммы существующим ключом отдельно; автоматическое скачивание релизов в GUI
пока не реализовано. Первый удалённый запуск workflow ещё требует проверки после push.

Команда после push (запускает сборку, не публикацию):

```sh
gh workflow run release-artifacts.yml --ref codex/setup-network-acceptance
```

MSYS2/Qt берутся из текущего репозитория пакетов; байтовая воспроизводимость EXE между
разными версиями тулчейна не заявляется. ZIP при одинаковых входах детерминирован.
[MSYS2 Action](https://github.com/msys2/setup-msys2) ·
[GitHub artifacts](https://github.com/actions/upload-artifact).

### Окружение Windows-сборки

GitHub использует UCRT64 и пакет `mingw-w64-ucrt-x86_64-qt6-static`.
Сборщик получает `-MsysEnvironment UCRT64`; Qt, компилятор и библиотеки берутся
из одного prefix. Старое локальное окружение доступно через `-MsysEnvironment MINGW64`.
Зависимости статической линковки указаны явно: qt6-static не устанавливает все
библиотеки из своих build dependencies. Проверка DLL после сборки сохранена.
Первый запуск 45612351368 завершил packages, но не начал компиляцию wizard:
`target not found: mingw-w64-x86_64-qt6-static`. Повтор старого запуска код не обновит;
после слияния исправления нужен новый Run workflow на main.
[Пакет UCRT64](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-qt6-static).

25.11.2026, следующий запуск: UCRT64 и helper-тесты прошли. Qt 6.12 загрузил
описания графических плагинов при find_package и остановился на WrapWebP; TIFF
также отсутствовал. В список добавлены libwebp и libtiff. Исключение imageformats
при линковке не отменяет чтение зависимостей при конфигурации. Предупреждение
Graphs2DImpl в этом журнале не является итоговой ошибкой и отдельно не исправлялось.
Подтверждение полного успеха требует нового GitHub-запуска после слияния.

Локальная сверка: разобраны configure.log, CMakeCache.txt, build.ninja и владельцы
файлов в pacman. WebP/TIFF были установлены на рабочем ПК и отсутствовали в CI.
Остальные внешние библиотеки покрыты списком, vulkan-loader приходит через qt6-static.
Это сопоставление Qt 6.11.2/MINGW64 с журналом Qt 6.12/UCRT64, не полный локальный
PASS UCRT64. Workflow сохраняет wizard-build-diagnostics даже при отказе: configure.log,
подробную строку линковки в build.log/build.ninja, CMakeConfigureLog.yaml, cache и
список версий пакетов. Эти файлы не входят в публичный ZIP мастера.

Состав внешних библиотек успешной локальной линковки: Brotli, OpenSSL, JPEG,
PNG, HarfBuzz, Graphite2, FreeType, bzip2, zlib, libb2 и PCRE2. TIFF, WebP и
Vulkan нужны также на этапе обнаружения компонентов; исключение плагина из
конечного EXE не освобождает от конфигурационных зависимостей Qt. Инструменты:
GCC/binutils, CMake, Ninja, pkgconf; binutils устанавливается вместе с GCC.
Проверки после правки: make all, новая статическая сборка MINGW64 и сохранение
шести диагностических файлов — PASS. Полная сборка UCRT64 остаётся проверкой GitHub.

Следующий журнал прошёл конфигурацию и выявил отказ линковки test-session-proof: все неопределённые символы относятся к Winsock и BCrypt. Замены .dll.a на .a недостаточно: статическому архиву нужны транзитивные системные зависимости. OPENSSL_USE_STATIC_LIBS теперь задан до find_package(Qt6), а OpenSSL::Crypto передаёт crypt32, ws2_32 и bcrypt каждому потребителю, включая тесты QtCore. Это исправление линковки, не установка дополнительных пакетов. Полный успех актуальной UCRT64/Qt 6.12 должен подтвердить новый запуск GitHub.

Локально после исправления: make all, статическая MINGW64-сборка, оба C++-теста, проверка встроенных образов и отсутствие сторонних DLL — PASS. Это не подтверждение сборки UCRT64 на GitHub.

## Проверка обновлённых артефактов 0.3.1 / 5.1.127

После push/CI/land владелец запускает `release-artifacts.yml` на main. Нужно сверить
`headSha` запуска с принятым HEAD, скачать итоговый `schoolbell-windows-preview-<SHA>`,
проверить SHA256SUMS и release-pair.json. Распаковать ZIP мастера в новую папку,
положить рядом ZIP 5.1.127, не подмешивать worker из локальной сборки.

Сначала проверить запуск EXE без MSYS2 в PATH, встроенные образы (`--check-firmware`),
выбор ZIP и обе темы. Затем отдельно принять на испытательном устройстве восстановление
OEM, OpenWrt, новую установку и установку поверх. Зафиксировать SHA ZIP и исходный
commit, результаты и ограничения. Только после этого подписать суммы и оформлять
первый релиз из этой же принятой пары. Проверка предыдущего локального EXE не
заменяет проверку скачанного артефакта; это не блокировка публикации владельцем.
