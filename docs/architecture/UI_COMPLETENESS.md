## 1. Правила законченного маршрута

Каждая операция должна иметь понятные исходное состояние, действие, результат,
обратное действие или объяснение необратимости, ошибку и путь восстановления.
Планируемые изменения ниже требуют отдельных веток и проверок.

- Просмотр не изменяет данные; правка относится к черновику, применение — к рабочей копии.
- Сохранить/отменить правки, назначить/снять, включить/выключить — видимые пары.
- Удаление показывает зависимости и последствия до подтверждения; скрытой подмены нет.
- Смена настроек не включает звук. Возврат из ошибки или повторный вход не повторяют действие.
- «Неизвестно» не равно «не выполнено»: сверяем результат по операции/ревизии, не повторяем POST вслепую.
- Симметрия не требует опасного обратного действия: звонок нельзя «отыграть назад»,
  подтверждение времени нельзя заменить возвратом часов, журнал не обязан иметь кнопку очистки.
- Для недоступной кнопки нужна причина и конкретное следующее действие, а не вечный busy.

## 3. Безопасность: что есть сейчас

Страница и её динамические endpoints находятся под `/admin/schoolbell` и используют
обычный вход LuCI. Родительский admin-маршрут LuCI требует сеанс; upstream 19.07
описывает cookie `sysauth` и login в
[luci-base.json](https://github.com/openwrt/luci/blob/openwrt-19.07/modules/luci-base/root/usr/share/luci/menu.d/luci-base.json).
Конкретную установленную сборку и обходы прямого URL нужно проверять отдельно.
Публичные CSS/JS сами по себе не дают права читать настройки или выполнять команды.

В нашем контроллере формы изменений проверяют `test_post_security()`. Для двоичных
MP3/SBB используется `Authorization: Bearer <CSRF token>` вместе с cookie-сеансом:
это обход ограничения передачи заголовков старого CGI, **не отдельный пароль и не
замена входа**. Есть серверные проверки типов/размеров, ссылок/ревизий, квот и
разрешённых действий; ограниченные повторы чтения не означают повтор записи.
Результаты команд времени привязаны к сеансу. Полноту этой защиты необходимо
проверить для каждого endpoint, а не считать доказанной одной общей функцией.

Ограничения:

- Сейчас используется административный доступ LuCI (на обычном стенде root).
  Отдельные роли дежурного/редактора не реализованы. Пароль администратора нельзя
  считать ограниченным паролем школьного звонка. Скрытие меню права не ограничивает.
- HTTP не шифрует пароль, cookie или резервную копию. Наличие пароля и CSRF не
  заменяет HTTPS. Настройка TLS/сертификата/доступа — отдельная установка с проверкой
  ресурсов и совместимости; текущая ветка не меняет uhttpd и сеть.
- Система предназначена для доверенной локальной сети; публикация LuCI в Интернет
  не входит в профиль. Для школы отдельно определить защищённую сеть управления,
  не смешивать её с гостевой/ученической сетью.
- Schoolbell журнал — журнал событий, не защищённый аудит действий конкретных людей.
  Общий root-вход не позволяет достоверно различать операторов. SBB проверяет
  целостность, но не является зашифрованным или подписанным архивом.

## 4. Целевая модель доступа (предложение)

Использовать существующий механизм сессий LuCI/rpcd, без самодельного хранения
паролей в schoolbell. Совместимость и достаточность ACL на 19.07 проверить
прототипом: текущие Lua-контроллеры нельзя считать ограниченными только из-за
назначенного имени роли. Каждая операция должна проверять полномочие на сервере;
системные действия выполняются узким проверяемым обработчиком.

| Роль | Предлагаемые разрешения |
| --- | --- |
| Просмотр | Статус/активный план без изменения; доступ к медиа и журналу согласовать отдельно |
| Дежурный | Просмотр, ручной звонок, остановка/Mute; без правки времени, импорта и сети |
| Редактор | Расписания/год/медиа, проверка и применение плана; экспорт копии по отдельному праву |
| Администратор | Пользователи/права, системное время/TZ, политика контроля, восстановление и обслуживание |

Точную матрицу утверждает владелец. Не выдавать дежурному root-пароль ради одной
кнопки. Повторное подтверждение особо важных действий не является вторым фактором
и не заменяет серверную авторизацию. На общих планшетах нужны видимый выход,
ограниченный срок сеанса и понятный повторный вход; CSRF-токены/пароли не сохранять
в localStorage, диагностике или публичных ссылках. Сеанс после logout должен быть
недействителен; pending-операция сверяется после входа, не отправляется повторно.

Проверки SEC-01…SEC-06 (локальные ID этого плана; расширяют AC-10/TC-29):

1. SEC-01: все динамические URL без сеанса/после logout/expiry не читают приватные данные и не действуют.
2. SEC-02: неверный/чужой/отсутствующий CSRF, неверный метод и content type отклоняются; загрузка без cookie не допускается одним Bearer.
3. SEC-03: каждая роль проверяется прямым запросом, включая скрытые кнопки; запрос к системному времени/restore от дежурного отклоняется.
4. SEC-04: чужие ID операций, конфликт ревизии и повтор POST не обходят права/допуск; после входа нет автоматического ручного звонка.
5. SEC-05: имена файлов/расписаний и импорт проверяются на XSS, path traversal, shell injection, размеры/квоты; токены отсутствуют в журнале/экспорте.
6. SEC-06: фактический HTTPS, доверие сертификату и разрешённые сетевые интерфейсы проверяются на стенде отдельно от mock/CI; отказ входа не превращается в обход авторизации.
