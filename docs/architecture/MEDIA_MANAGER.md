# Изолированный менеджер медиатеки

[English](MEDIA_MANAGER.en.md). Реализация ТЗ 1.19, частичное покрытие контрактов
1.17/1.18. Это библиотека для подготовленных объектов и тестовый стенд, не
установленная служба, не публичный веб-API и не готовый импорт произвольных MP3.

## Состав и запуск

- `schoolbell.media_codec`: строгий JSON и SHA-256 небольших служебных данных.
- `schoolbell.media_fs`: приватный файловый backend nixio; SHA-256 файлов через
  установленный sha256sum. Linux host использует тестовую C-обёртку syscalls.
- `schoolbell.media_manager`: снимки, публикация, сверка, fallback и очистка.
- `test-media-manager.sh`: реальные host-файлы и отдельные Lua-процессы,
  25 аварийных выходов в точках фиксации, дополнительные проверки отказов.

Штатная проверка: `make ci-schoolbell` либо `sh packages/schoolbell/tests/test-media-manager.sh`
с Lua 5.1, C compiler, development headers и python3. Скрипт не подключается к
роутеру; стенд на роутере запускается отдельно по разрешению пользователя.

```lua
local fs = require('schoolbell.media_fs').new(private_existing_root)
local manager = require('schoolbell.media_manager').new(fs, {
    ownership_safe = function()
        return isolated_fixture_has_no_player
    end
})
local state = manager.recover()
-- manager.commit(operation_id, expected_generation, documents, imports, initialize)
-- manager.lookup(operation_id); manager.cleanup(); manager.close()
```

Ownership callback по умолчанию запрещает работу. True допустимо только при
доказанном исключительном владении и отсутствии старого проигрывателя. В тестах
нет никакого проигрывателя. Это не реализованный механизм обнаружения детей
production-службы. Приватный корень заранее существует и имеет права 0700;
один менеджер удерживает POSIX lockf на стабильном `.lock` до close. Нельзя удалять
lock-файл или менять доверенный корень/его предков. Повторный экземпляр в том же
Lua-процессе также отвергается. Код не является защитой от злонамеренного root.

## Подготовленный комплект

Documents — таблица строк JSON под четырьмя фиксированными именами. Catalog
имеет оболочку `{"melodies": [...]}` и поля из MEDIA_FORMAT; этот этап принимает
только `source=user`. Имя до 256 байт, ID соответствует существующей модели
`[A-Za-z0-9_-]` длиной 1–64. Импорты — доверенная таблица SHA-256 → абсолютный путь
к регулярному подготовленному файлу. Размер, хеш и численные audio-поля проверяются;
достоверность MP3/audio обеспечивает вызывающий подготовительный слой, а не этот
менеджер. Используются известные исходные MP3, звука нет.

Settings — подготовленный валидный JSON. Schedules и plans на этом этапе —
списки зависимостей `{"references": [{"id": "bell", "revision": "..."}]}`.
Каждая пара проверяется против каталога. Это не формат календаря или новый
пользовательский формат настроек; реальные календарные данные/миграции и их
семантический валидатор ещё должны быть подключены. Список не может использоваться
для сокрытия ссылок настоящего плана: такие планы этот API пока не принимает.

Подготовленные объекты копируются блоками до 16 КиБ, сверяются с хешем, затем
синхронизируются. Ревизии не перезаписываются. Snapshot ID равен переданному ID
операции: 32 lowercase hex; существующий каталог никогда не переиспользуется.
ID создаёт доверенный caller, генератор здесь не реализован.

## Указатели и фиксация

Current/recovery имеют поля generation, current, previous, checksum. Ссылка:
`{snapshot, sha256}`. Previous может быть JSON null; поколение 1..2147483647,
без wrap. Checksum — SHA-256 строк с завершающим LF: schoolbell-pointer,
поколение десятичными цифрами, ID текущего, его хеш, ID предыдущего, его хеш.
Для отсутствующего предыдущего последние две строки содержат `-`.
Это проверка повреждения, не аутентификация.

Snapshot.json содержит storage_version=1, operation_id, generation и files —
ровно четыре записи name/size_bytes/sha256. Хешируется точное содержимое файлов;
само описание проверяется хешем из указателя. Подготовленный снимок проверяется
полностью до публикации.

Последовательность: объект → снимок → синхронизированная копия старого current
в recovery → временный current → rename → fsync родителя. При перемещении
между staging и конечным каталогом синхронизируются оба каталога. Saved только
после всех барьеров. Ошибка во время потенциальной публикации даёт
needs_recovery, ранее — rejected; несовпавшее поколение — conflict.

Инициализация требует initialize=true, expected_generation=0 и пустого объекта/
снимков без указателей. Случайно пустая или повреждённая установленная библиотека
не инициализируется автоматически. После неудачной первой инициализации с
оставшимися файлами нужна явная административная проверка, не слепой повтор.

## Восстановление и очистка

Recover возвращает ready, empty, paused либо recovery_required. Проверяет current
и весь комплект; затем предыдущий из целого current, далее current/previous из
проверенного recovery. Fallback остаётся paused. По именам/mtime кандидаты не
выбираются. Повторный запуск не воспроизводит заявки. Lookup сообщает retained
либо unknown; retained означает проверенный сохранённый снимок по указателю,
не историческое доказательство доставки ответа saved. Unknown не означает отказ.
Автоматическая запись указателя после fallback и UI-подтверждение не реализованы.

Cleanup сначала проверяет текущий и предыдущий снимки, синхронизирует recovery
как копию current, затем удаляет непривязанные снимки, объекты и собственные
временные файлы. Ошибка даёт cleanup_failed, не отменяет коммит. Hold(hash)
возвращает идемпотентную функцию release для дополнительного запрета GC объекта;
close с живыми удержаниями запрещён. Это локальное удержание GC, не привязка
к очереди/FD-lease media_linux. Все реальные владельцы планов/backup/процессов
должны учитываться перед production-интеграцией.

## Ограничения и проверки

Строгий декодер ядра ограничен 16 КиБ на документ: этот этап сознательно принимает
не более 16 КиБ каждого JSON (в том числе catalog), хотя договорённый будущий
потолок catalog — 64 КиБ. Остальные защитные проверки размера/длительности,
числа записей и запаса реализованы; реальный диск может отказать раньше.
Обход каталога ограничен 512 записями. Нет заверений о RAM всей службы,
произвольных многолетних планах или достижимости всех максимальных квот.

TC-91: host-матрица 25 отдельных аварийных выходов, hash/JSON, lock, conflict,
битый объект/указатели, ссылки, лимиты, место, fsync, GC/hold и запрет неизвестного
владения. TC-92: тот же изолированный менеджер в /tmp и отдельном постоянном
каталоге MR3020; изолированный PASS: 25 точек на каждой ФС плюс негативные проверки; стенд удалён. Это завершение
процесса, а не отключение питания. Проверка не доказывает физическую долговечность
JFFS2/flash. Нет core/очереди, службы, произвольного upload, bundled resolver,
браузерного API, звука или установки IPK.

На MR3020 выявлены и учтены особенности nixio mode=700/600 и 32-битного форматирования uint32 Lua. Измеренный VmHWM тестовых процессов 1200–1544 КиБ, не бюджет будущей службы. Core/demo не перезапускались, контрольные хеши установленного набора сохранены.
