# Контракт адаптера проигрывателя schoolbell

[English](PLAYER_ADAPTER.en.md) · [ТЗ 1.8](../requirements/TECHNICAL_SPECIFICATION.md)

Контракт принят, системный адаптер не реализован. Эта памятка не меняет API
[изолированной очереди](PLAYBACK_QUEUE.md). Нормативные пункты: 3.2.3,
3.5.2/3.5.7–3.5.9 и 3.6.1–3.6.10 ТЗ; проверки TC-43–49 плановые.

## Процесс и результат

Один владелец schoolbell управляет очередью и дочерними процессами ресурса.
Первый backend — madplay, профиль `--no-tty-control -a 0 -R 48000 -o /dev/dsp`.
Executable доверенный, аргументы передаются раздельно; пользовательские строки
не превращаются в shell-команду. Это описание профиля, не команда запуска теста.

| Фаза | Смысл |
| --- | --- |
| Принята | В очереди, конкретная ревизия файла удержана |
| launching | Разрешение выдано, подтверждение запуска ещё ожидается, ресурс занят |
| Запуск подтверждён | Программа запущена; слышимость не подтверждена |
| Завершена | Получен статус своего дочернего процесса: exit с кодом либо сигнал |
| Неопределённость | Ресурс и файл удерживаются, повторный запуск запрещён |

PID не доказывает успешный exec. Подтверждение запуска асинхронное;
waitpid с WNOHANG получает завершение без ожидания в рабочем цикле.
Быстрый выход не должен потеряться между подтверждением запуска и наблюдением.
Чужой PID, исчезновение PID или строка лога не доказывают завершение нашей попытки.
Обычный exit 0 — успешный выход программы, не доказательство слышимого звука.

После подготовки файла проверяются TTL и применимый UTC непосредственно перед
разрешением запуска. TTL не продлевается. Граница — выдача разрешения, а не
точное время exec/звука; задержки ОС измеряются отдельно. Уже разрешённый запуск
не прерывается по сроку. Активный stop не входит в первую версию.

Таймаут подтверждения запуска отдельный от TTL. Истечение даёт неопределённость,
а не освобождение ресурса или автоматический повтор. stdout/stderr ограничены
по хранению и работе за проход; заполненный канал не должен блокировать player.

## Владение мелодией

До подтверждения приёма закрепляется конкретная существующая ревизия медиа.
Нет нужной ревизии — отказ, без подстановки другой. Отказ допуска освобождает
временное удержание. Замена создаёт новую неизменяемую ревизию; pending и active
остаются на прежней. Перед запуском требуется защищённый от подмены файл.

Ссылка заявки освобождается после отмены/expiry, доказанного отказа без процесса
или подтверждённого завершения. Терминальная квитанция может оставаться в памяти
без удержания медиа. Неопределённость удерживает файл. План, другая заявка,
backup и откат имеют независимые ссылки: освобождение одной не означает удаление.

Передача открытого файла через stdin принята в р.1.9 при условии проверки madplay.
Формат хранения и атомарная публикация медиатеки ещё не выбраны. Строка media_revision в текущей Lua-модели не реализует эти гарантии.

## Сбой и следующий этап

После аварии новый исполнитель не начинает звук, пока не исключён старый
проигрыватель. PID-файла недостаточно. Потерянный результат не означает, что
мелодия не играла; неизвестную заявку автоматически не повторяем.
Этот контракт не вводит durable queue, exactly-once, stop или политику paused
после reboot. При неопределённости сохраняется блокировка и диагностика.

Механизмы и форма API приняты в ТЗ 1.9: [System API](PLAYER_SYSTEM_API.md). Реализация отсутствует; поля, наблюдение executable и бюджеты уточнены в [ТЗ 1.10](PLAYER_RESULTS.md); проверки конкретного madplay впереди.

Плановые host-тесты: argv/exec/быстрый exit (TC-43), сроки (TC-44), коды/сигналы/
PID (TC-45), потеря подтверждения (TC-46), замена/удаление медиа (TC-47),
переполнение вывода (TC-48), авария/новый владелец (TC-49). Подменный процесс
работает без аудиоустройства. Реальный звук и target требуют отдельного этапа.
