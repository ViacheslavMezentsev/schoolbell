1. Firmware identity

Case label: TL-MR3020 EU v3.30. The new unit reported 1.8.0 0.9.1 Build 250625 Rel.56805n. The official ZIP contains a 1.8.0 BIN despite 1.7.0 in the ZIP name. Keep the original BIN unchanged.

Hashes were computed locally after HTTPS download; they are not a TP-Link signature. Matching release numbers do not prove identical installed Flash contents.

Recovery is a bootloader function, not necessarily a separate firmware release. The PDF in the OEM ZIP documents web upgrade, not TFTP. The initial OpenWrt support commit describes TFTP with an OpenWrt image; the wiki mentions OEM firmware with its header removed but provides no verified recipe for our Build 250625. Acceptance of the original BIN by this EU v3.30 bootloader is unverified. Do not apply v1 trimming instructions or modify bytes by guesswork.

2. Dedicated Ethernet connection

Laptop → USB–Ethernet → new MR3020 LAN. Router power is separate. Keep the laptop’s main Ethernet unchanged; no bridge or Internet sharing is needed.

  1. Save the USB adapter’s settings, DNS and routes. Identify that adapter by name and identifier.
  2. The documented v3 recovery server address is 192.168.0.225/24, without gateway or DNS on this adapter. It is not the normal management address.
  3. Check subnet/VPN conflicts. Change only the dedicated adapter; do not disable the entire firewall or VPN.
  4. In Tftpd64 select Server interfaces: 192.168.0.225, a dedicated Current Directory and read-only TFTP. Disable DHCP, DNS and SNTP services. Scope the Windows Firewall rule to that executable, USB interface, local IP and recovery subnet.

3. Observe a request before serving firmware

The active directory must be empty. Do not select an OpenWrt or OEM image directory. Once a restart is separately authorized, start the server, turn off the router, hold Reset/WPS and apply power. The v3 support commit describes roughly 6–7 seconds until a request. Record client IP, requested filename, timestamp and server reply. The documented name is tp_recovery.bin. With an empty directory, expect a file-not-found error rather than a firmware transfer.

This checks the request path, not Flash writing. The exact EU v3.30 behaviour and button timing still need bench verification. A failed ping alone does not establish a recovery failure.

4. Writing is a separate experiment

First agree the exact file, SHA-256 and delivery method after checking bootloader requirements. Stop the server, prepare only the approved tp_recovery.bin and re-enter recovery. Transfer may immediately trigger writing without another prompt. Keep power and cable connected.

Record request, completed transfer, OS startup, version and Ethernet/Wi-Fi separately. Transfer success is not recovery success. A conf.bin settings backup does not include the bootloader or radio calibration. Afterwards stop the server, remove only the temporary firewall rule and restore saved USB adapter settings.

Current status: files and server configuration prepared; address/firewall not applied; server not started; bootloader request/write/boot not tested. The running OEM web interface is not required for bootloader TFTP.

5. Long-term preservation

The original ZIP, BIN, PDFs/license, source-page snapshot and manifest are stored locally. Pages publishes our RU/EN reference, exact hashes and source links; OEM binaries stay outside Git. No public mirror has been published.

Keep at least two independent copies. Before publishing an OEM archive, check redistribution terms for the complete bundle: an included GPL document does not cover every component automatically. Then pin an immutable release asset and add its mirror URL to the JSON. Preserve names, hashes, origin, date, licenses and any transformation history.

Each future model needs its own artifact record and tests. Recovery success on this MR3020 will not establish support for another hardware revision.
